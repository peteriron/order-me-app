# A Shared Catalog travels in the link's fragment, and doesn't reach installed iPhone apps

A friend gets the Operator's Items by scanning a QR code (or opening a copied link). There is no server, so the Catalog itself has to ride in the link. We put it in the `#fragment` of the app's normal address (`…/order-me-app/#items=…`): browsers never send the fragment to the server, so GitHub Pages serves the app as usual and the Items stay between the two phones. Only each Item's name, category and emoji travel (no ids, History, Round, settings or pins), as short text, deflated and base64url-encoded, so the 21-Item starter Catalog makes a link of about 330 bytes and a QR code that scans easily off a phone screen. Opening the link replaces the Catalog (silently on a first launch, otherwise after a confirm), keeps History (ADR-0001) and clears the fragment.

The accepted cost: on an iPhone, a friend who has **already added the app to the Home Screen** doesn't receive the Items there. Scanning a QR code or tapping a link opens it in Safari, and an installed web app can't capture it: web.dev notes "It's impossible to capture URLs on PWAs installed on iOS and iPadOS from Safari" ([Learn PWA: OS integration](https://web.dev/learn/pwa/os-integration/)). Safari and the Home Screen app also keep separate website data, so importing in Safari doesn't change the installed app's Catalog. WebKit states this separation for Mac web apps ("After a user adds a web app to the Dock, no other website data is shared", [WebKit features in Safari 17.0](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/)); Home Screen web apps on iOS behave the same way, though neither source says so for iOS in so many words. On Android and in any browser tab, the link works. We accept this rather than add a server or a paste-a-code import screen: the common case is a friend who doesn't have the app yet, and for them the link is how they get it.
